# Voice Study Buddy 🎓🎙️
"Ask. Listen. Learn."

## Overview

Voice Study Buddy is a simple web-based AI voice tutor. A student clicks a
mic button, asks a study question out loud, and hears a short spoken answer
generated by an LLM and voiced by **Rime**. The one feature this project is
built around: **you can interrupt the AI while it's speaking and redirect
it to a new question**, without the old answer ever finishing or resuming.

## Problem Statement

Most "voice assistant" demos are really just a chatbot with a play button:
type or say a question, get one static reply, done. Real conversations
aren't like that - people interrupt, redirect, and change their mind mid
-sentence. Study tools should let students do the same instead of forcing
them to sit through an answer they no longer want.

## Why Voice?

Voice is faster than typing when you're stuck mid-problem, and it's how
people actually ask follow-up questions ("wait, simpler please") in real
conversation. But voice-only interfaces only feel natural if you can talk
over them - otherwise every mistake wastes 10-20 seconds waiting for the AI
to finish before you can correct it.

## Solution

A minimal pipeline: **browser mic → speech-to-text → LLM tutor → Rime
text-to-speech → browser playback**, with a "generation ID" mechanism
running through the whole stack so that a new question always wins over an
old, still-in-progress one - both on the server and in the browser.

## Main Feature: Interruption & Recovery

This is the core, load-bearing feature of the project (see [How
Interruption Works](#how-interruption-works) below and
[RIME_EVIDENCE.md](RIME_EVIDENCE.md) for the acceptance test).

## Features

- 🎤 Voice input via the browser's built-in speech recognition
- 🧠 Short, simple, tutor-style answers from an LLM
- 🔊 Natural-sounding speech via Rime's `coda` model
- 🛑 One-click interruption that stops audio and starts a new question
- 🔁 Generation-ID based cancellation that greatly reduces the chance of a stale answer playing
- 📊 Live interruption counter and Rime status indicator
- ⚠️ Friendly error handling for mic, network, LLM, and Rime failures

```
     │
```

## Prerequisites

- Python 3.10+
- A modern browser with microphone support (Chrome or Edge recommended -
  Safari also supports `SpeechRecognition`; Firefox currently does not)
- A [Rime API key](https://app.rime.ai/tokens)
- An [Anthropic API key](https://console.anthropic.com/settings/keys)

```bash

python -m venv venv

pip install -r requirements.txt
```

```bash
cp .env.example .env
```

Then edit `.env`:

```env
RIME_API_KEY=your-rime-key-here
LLM_API_KEY=your-anthropic-key-here
STT_API_KEY=
```

`STT_API_KEY` is unused by default (see [How STT Works](#how-stt-works)
below) - it's a placeholder for a future upgrade.

## Running the Backend

```bash
cd backend
uvicorn main:app --reload --port 8000
```

You should see Uvicorn print `Application startup complete.` If you instead
see `KeyError` or a message about a missing key, double check your `.env`
file is filled in and located in the project root.

Nothing extra to run! FastAPI serves the frontend for you. Once the backend

## How Rime Is Used

`backend/rime.py` sends the tutor's answer text to Rime's TTS endpoint and
gets back MP3 audio bytes:

- **Endpoint:** `https://users.rime.ai/v1/rime-tts`
- **Model:** `coda` (Rime's current flagship model; the older `arcana`
  model stops serving cloud traffic on 2026-08-15 per Rime's changelog, so
  this project targets `coda` directly)
- **Voice:** `astra` (Rime's documented starter voice for Coda)
- **Format:** MP3, via the `Accept: audio/mpeg` header
- **Auth:** `Authorization: Bearer <RIME_API_KEY>` header, server-side only

The Rime API key is read once from the environment in `rime.py` and never
sent to, or accessible from, the browser.

## How STT Works

Speech-to-text happens **in the browser**, using the built-in
`SpeechRecognition` Web API (`frontend/script.js`). This needs no API key
and no extra network hop, which keeps the hackathon build simple and fast.

`backend/stt.py` exists as a documented placeholder/seam so a real STT API
(Deepgram, AssemblyAI, Whisper, etc.) can be swapped in later without
touching the LLM, Rime, or interruption logic - see the comment at the top
of that file for the exact steps.

## How Interruption Works

Every question - whether it's the first one or one that interrupts the AI
mid-sentence - gets an incrementing **generation ID**, tracked independently
in the browser and on the server:

1. **Browser side** (`frontend/script.js`): `currentGenerationId` increases
   every time a new question starts. When a server response comes back, the
   browser checks whether it still matches `currentGenerationId` before
   playing its audio. If not, the response is silently discarded.
2. **Server side** (`backend/main.py`): `latest_generation_id` tracks the
   highest generation ID seen. Before calling the LLM, before calling Rime,
   and right before returning audio, the server checks whether the current
   request's generation ID is still the latest one. If a newer request has
   since arrived, the server aborts and returns `409 Conflict` instead of
   audio.
3. **Clicking "🛑 Interrupt"** immediately pauses the `<audio>` element,
   aborts any in-flight fetch request, and bumps the generation ID - which
   invalidates anything still processing - then reopens the microphone for
   the new question.

Two independent checks (browser + server) make it very unlikely that stale
audio plays, even under real network race conditions such as an old
response arriving after a new one has already started. This is a
check-then-act pattern over a network, so it reduces the risk rather than
eliminating it entirely - see the note in `backend/main.py`'s module
docstring for the specific (narrow) race window this can't close.

## Known Limitations

- **Interruption is button-triggered, not voice-activity-detected.** True
  "barge-in" (the AI stopping the instant you start talking over it, with no
  button) needs continuous microphone monitoring during playback, which
  adds real complexity (voice activity detection, echo cancellation) that
  is out of scope for a beginner hackathon build. Clicking "🛑 Interrupt"
  simulates the same outcome (stop the old answer, immediately accept a new
  question) in a much simpler way.
- Browser `SpeechRecognition` support varies (works well in Chrome/Edge;
  not supported in Firefox at the time of writing).
- No conversation memory across questions - each question is answered
  independently (kept simple on purpose).
- Single-process generation-ID tracking (a module-level integer) is fine
  for a single `uvicorn` worker but would need a shared store (e.g. Redis)
  if deployed with multiple worker processes.
- No user accounts, database, or persistence - conversation history is only
  kept in the browser tab for the current session.

## Security

- `RIME_API_KEY` and `LLM_API_KEY` are read only in `backend/rime.py` and
  `backend/llm.py` and are never sent to, or readable from, the browser.
- `.env` is listed in `.gitignore` and is never committed.
- `.env.example` contains empty placeholders only, never real keys.
- Error messages returned to the browser include the upstream service's
  error text but never the API key value itself.
- User input (the question text) is passed to the LLM as plain data, not
  interpolated into any command or query string.
